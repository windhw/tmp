全景图

X11 桌面的完整分层

下面是一台普通 Linux 桌面（X11 会话）上各组件的位置。上半部分跑在用户空间，下半部分是内核和硬件。实线是画面往下走到显示器的路径，虚线是键盘鼠标事件往上走到应用的路径。

先抓住主干。应用不直接碰显卡，也不直接碰显示器。它们要么把"开窗口、画东西"的请求交给 X Server，要么借 Mesa 自己用 GPU 画好再交给 X Server。X Server 通过内核里的 DRM/KMS 驱动指挥显卡，显卡再把显存里的那一帧图像持续送到显示器。

七个概念

从硬件往上，逐个拆开

顺序和全景图一致，从最底层的显示器讲到最上层的应用，最后是两个"拓展玩法"：虚拟显示和 VNC。

硬件层

显示器

Monitor / Display

一块"哑"设备：只把收到的像素信号变成光，不知道什么是窗口，也不知道对面是 Linux。

  • 通过 HDMI、DisplayPort 或笔记本内部的 eDP 接到显卡的输出口（内核里叫 connector）。
  • 以固定的刷新率（60Hz、144Hz……）一帧一帧地接收完整画面。每一帧都是显卡从显存里读出来、按行扫描发送的。
  • 插上时通过 EDID 数据告诉显卡：我叫什么、支持哪些分辨率和刷新率、物理尺寸多大。系统据此列出可选分辨率，并计算 DPI。
  • 多显示器时，每块屏对应显卡上的一路输出。把它们拼成扩展桌面还是镜像，是上层（X 的 RandR 扩展或 Wayland 合成器）的决定。
查看：xrandr cat /sys/class/drm/card*-*/status edid-decode
驱动层

显卡与显卡驱动

GPU · DRM/KMS · Mesa

显卡负责存放画面、执行绘图运算、把画面送给显示器；驱动让 Linux 能指挥它。Linux 的显卡驱动分成内核和用户态两半。

显卡（GPU）硬件里有三样关键的东西

  • 显存与帧缓冲（framebuffer）：一块内存区域，存着"屏幕现在应该显示的像素"。集成显卡用的是系统内存的一部分。
  • 显示引擎：按显示器的刷新率不断读取帧缓冲，经 encoder 和 connector 发到线缆上，这叫扫描输出（scanout）。
  • 渲染引擎：成千上万个计算核心，执行 OpenGL/Vulkan 翻译过来的绘图命令，把结果写回显存。

内核态驱动：DRM / KMS

  • KMS（Kernel Mode Setting） 设置分辨率、刷新率，决定"哪块 buffer 显示到哪个屏幕"，并在垂直同步时翻页（page flip）。
  • DRM（Direct Rendering Manager） 管理显存 buffer、在多个程序间安全地共享 GPU、接收用户态提交的命令。
  • 具体驱动模块：Intel 的 i915/xe、AMD 的 amdgpu、NVIDIA 开源的 nouveau 或官方的 nvidia + nvidia-drm。设备节点是 /dev/dri/card0（控制显示）和 /dev/dri/renderD128（只渲染）。

用户态驱动：Mesa（或 NVIDIA 专有库）

  • 实现 OpenGL 和 Vulkan 这些 API，把应用的绘图调用翻译成某款 GPU 能懂的命令，再交给内核驱动。Mesa 里有 iris、radeonsi、RADV、ANV、NVK 等针对不同显卡的实现。
  • 没有可用 GPU 时，Mesa 的 llvmpipe 用 CPU 软件模拟 OpenGL，很慢但能用，虚拟显示里常见。

Xorg 自己的显示驱动（DDX）

  • Xorg 还需要一个"把自己接到显卡上"的模块。现在绝大多数机器用通用的 modesetting：调用 KMS 设置画面，用 glamor（基于 OpenGL）加速 2D。老的 xf86-video-intel 等专用 DDX 已逐渐淘汰；NVIDIA 专有驱动则带自己的 nvidia DDX。
查看：lspci -k | grep -A3 VGA glxinfo -B ls -l /dev/dri
显示服务器层

X Server

X Window System · Xorg

X11 体系的"显示总管"：独占屏幕和键鼠，所有图形程序都要连上它，才能开窗口、收输入。

  • X Window System 诞生于 1984 年的 MIT，协议第 11 版（X11）在 1987 年定型并沿用至今。Linux 上最常见的实现是 Xorg（X.Org Server）。
  • 它是一个服务器进程，应用是客户端。客户端通过 Unix socket /tmp/.X11-unix/X0（或 TCP 端口 6000+N）连接，用环境变量 DISPLAY=:0 指定连哪一个 X Server。
  • 维护一棵窗口树：每个窗口的位置、大小、层叠关系；根窗口就是整块屏幕。
  • 分发输入：根据鼠标位置和焦点，把按键、点击事件发给对应窗口的客户端。
  • 绘图：早年客户端让 X 画线、画字、填矩形；现在的程序基本自己画好整张图，X 只负责把图贴上去。
  • 靠扩展演进到今天：XRandR（多屏、分辨率旋转）、Composite（窗口离屏合成）、GLX / DRI3 / Present（3D 直接渲染）、XInput2（触控、多指针）、XKB（键盘布局）。
  • 设计原则是"只提供机制，不提供策略"：X Server 不画标题栏，也不决定新窗口放在哪，这些交给窗口管理器。

反直觉的命名：X Server 运行在有屏幕和键盘的那台机器上，因为它"服务"的是显示和输入。用 ssh -X 登录远程服务器跑程序时，远程机器上的程序是客户端，它连回的是你面前这台电脑上的 X Server。

查看：echo $DISPLAY xdpyinfo | head ls /tmp/.X11-unix/
窗口管理层

窗口管理器

Window Manager · Compositor

一个享有特权的 X 客户端，决定每个窗口放在哪、多大、谁在前面、带什么样的边框和标题栏。

  • 怎么拿到权力：它向 X Server 申请根窗口的 SubstructureRedirect。此后任何程序想显示、移动、缩放窗口，X Server 都会先把请求转给窗口管理器审批。同一时刻只能有一个窗口管理器。
  • 职责：窗口摆放、层叠或平铺、焦点切换、画边框和标题栏（叫"窗口装饰"）、最大化最小化、多个虚拟桌面、全局快捷键。
  • 不装会怎样：程序照样能跑，但窗口全堆在左上角，没有标题栏，拖不动也关不掉。可以用 Xvfb 加一个 xterm 亲手试试。

三种类型

  • 层叠式（像 Windows 那样窗口可以重叠）：Openbox、Fluxbox、xfwm4、IceWM。
  • 平铺式（自动把屏幕切成不重叠的块）：i3、awesome、dwm、bspwm。
  • 合成式：自带合成器（compositor）。开启 Composite 扩展后，每个窗口先画到自己的离屏 buffer，再由合成器用 GPU 拼成整屏，于是能做透明、阴影、动画和防撕裂。GNOME 的 Mutter、KDE 的 KWin 都是。不带合成的窗口管理器可以另配独立合成器 picom。

和桌面环境的区别：桌面环境 = 窗口管理器 + 面板/任务栏 + 设置中心 + 文件管理器 + 一整套应用。GNOME 用 Mutter，KDE Plasma 用 KWin，Xfce 用 xfwm4。

查看：wmctrl -m echo $XDG_CURRENT_DESKTOP
应用层

GUI 应用程序

X Client · Wayland Client

真正干活的程序：浏览器、终端、编辑器、游戏。它们在 X11 里叫 X 客户端，在 Wayland 里叫 Wayland 客户端。

  • 很少直接讲协议，而是用 GUI 工具包：GTK（GNOME 系）、Qt（KDE 系）、Electron/Chromium、SDL（游戏）、Java Swing、Flutter。工具包底层再调 Xlib/XCB（X11）或 libwayland-client（Wayland）。
  • 程序结构是一个事件循环：等待事件（按键、点击、窗口大小改变、需要重绘），更新自身状态，重画自己的窗口内容，再继续等。
  • 现代程序都自己渲染：用 CPU（Cairo、Skia 软件渲染）或 GPU（经 Mesa 的 OpenGL/Vulkan）把整张窗口画好，再把这张"图"交给显示服务器。
  • 同一个 GTK/Qt 程序既能跑在 X11 也能跑在 Wayland，工具包启动时自动选择后端。可以用 GDK_BACKEND=x11 或 QT_QPA_PLATFORM=wayland 强制指定。

拓展玩法

虚拟显示

Virtual / Headless Display

机器上没有显示器，甚至没有显卡，也"假装有一块屏"，让图形程序照常运行。

  • 原理：显示服务器只需要一块能写像素的帧缓冲，它并不关心这块缓冲最后有没有送到真的显示器。把帧缓冲放进普通内存，就得到了一块虚拟屏。
  • Xvfb（X Virtual FrameBuffer）：一个完整的 X Server，帧缓冲在内存里，CPU 软件渲染，没有任何输出。CI 里跑浏览器测试、无头截图最常用。xvfb-run 一条命令就能包装一个程序。
  • Xvnc：X Server 和 VNC 服务端合二为一，TigerVNC/TurboVNC 的 vncserver 启动的就是它。虚拟屏的内容可以被远程看到。
  • Xorg + dummy 驱动（xf86-video-dummy）：完整的 Xorg，配一个假显示器驱动，能用 RandR 等全部扩展。
  • 有 GPU 但没接屏：通过内核参数注入 EDID（drm.edid_firmware），或者插一个"HDMI 欺骗器"（假负载），让显卡以为接了显示器，从而获得完整硬件加速。游戏串流、GPU 云桌面常用。
  • Wayland 下：合成器自带 headless 后端，例如 weston --backend=headless、Sway 的 WLR_BACKENDS=headless、mutter --headless --virtual-monitor 1920x1080。

拓展玩法

VNC

Virtual Network Computing · RFB

把"一块屏幕的像素"通过网络传到另一台电脑上显示，同时把那边的键盘鼠标操作传回来。

  • 底层协议叫 RFB（Remote Framebuffer）。它工作在帧缓冲这一层：不关心窗口和应用，只传送屏幕上发生变化的矩形区域的像素，并用 Tight、ZRLE、JPEG 等编码压缩。所以它非常通用、跨平台，但高分辨率或播放视频时比较吃带宽。
  • 两端角色：VNC 服务端（被看的那台）和 VNC 客户端 / Viewer（看的那台，如 TigerVNC Viewer、RealVNC、Remmina、浏览器里的 noVNC）。端口是 5900 + 显示号，:1 就是 5901。
  • 两种用法（见下方示意图）：共享一块已有的真实桌面（x11vnc、Wayland 下的 wayvnc）；或者新建一个独立的虚拟桌面（Xvnc，每个用户一个，机器上没有显示器也行）。
  • 经典 VNC 默认不加密（有的实现支持 VeNCrypt/TLS）。在公网上通常走 SSH 隧道：ssh -L 5901:localhost:5901 user@server，再连本机的 5901。
  • 和 ssh -X 的区别：X11 转发传的是 X 协议命令，只转发单个程序的窗口，网络延迟高时很卡；VNC 传的是整屏像素。其他同类方案还有 RDP（xrdp、GNOME 远程桌面）、SPICE（虚拟机）、NoMachine 和 Sunshine（视频流编码）。
试试：vncserver :1 -geometry 1920x1080 x11vnc -display :0 -localhost
把各层串起来

按下 A 键，到屏幕上出现 "a"

在一个 X11 + 合成器的桌面上，你在终端里敲下一个字母，数据会穿过整个图形栈一来一回。整个过程通常在 10 到 50 毫秒之间完成。

  1. 键盘

    按下 A 键，键盘通过 USB 发出一个 HID 报告，里面是这个键的扫描码。

  2. 内核

    USB HID 驱动解析报告，交给 input 子系统，/dev/input/event3 上出现一条 KEY_A 按下 事件。

  3. libinput

    Xorg 加载的 libinput 输入驱动读到这条事件，转换成 X 的 KeyPress。XKB 根据当前键盘布局把它翻译成字符 "a"。

  4. X Server

    查窗口树和输入焦点（焦点是窗口管理器之前设置好的），把 KeyPress 事件写进终端程序的 socket。

  5. 终端程序

    事件循环被唤醒，把 "a" 追加进缓冲区，并重新渲染受影响的那一行（用 Cairo 或 OpenGL）。

  6. 终端程序

    把画好的新窗口内容交给 X Server（通过共享内存或 DRI3/Present 传递 buffer）。

  7. 合成器

    X Server 发出 Damage 通知，告诉合成器这个窗口变了。合成器用 OpenGL（经 Mesa 驱动 GPU）把所有窗口重新拼成整屏画面。

  8. DRM/KMS

    整屏画面画进一块新的 buffer，通过 KMS 请求"下一次垂直同步时切换到这块 buffer"（page flip），避免画面撕裂。

  9. GPU

    显示引擎在下一个刷新周期读取新的帧缓冲，经 HDMI/DP 线缆逐行发出。

  10. 显示器

    点亮对应像素，你看到了 "a"。

另一种架构

Wayland：去掉中间人

Wayland 是 2008 年由 X 开发者 Kristian Høgsberg 发起的一套新的显示协议（加上参考库 libwayland），不是 Xorg 的新版本，也不是某一个具体程序。它的核心想法是：既然现代应用都自己画好整张窗口，合成器又总要把所有窗口重新拼一遍，那 X Server 夹在中间就只剩转手传话了，不如直接拿掉。

于是 X11 里的三个角色——显示服务器、窗口管理器、合成器——在 Wayland 里合并成了一个进程，统称 Wayland 合成器（compositor）。

X11 的六步

  1. 内核把输入事件交给 X Server。
  2. X Server 判断落在哪个窗口，转发给应用。但窗口可能已被合成器缩放或做了动画，X 并不知道它在屏幕上的真实样子，只能按自己窗口树里的位置去猜。
  3. 应用画好新内容，交回 X Server。
  4. X Server 发 Damage 通知给合成器："这个窗口变了"。
  5. 合成器重新拼出整屏，再交回 X Server。
  6. X Server 通过 KMS 送去显示。

Wayland 的四步

  1. 内核把输入事件直接交给合成器。
  2. 合成器清楚每个窗口在屏幕上的真实位置和变换，准确地把事件发给对应的应用。
  3. 应用自己画好一块 buffer（CPU 用 wl_shm 共享内存，GPU 用 linux-dmabuf），然后 commit 给合成器。
  4. 合成器拼好整屏，通过 KMS 送去显示，每一帧都是完整的，设计上就不会撕裂。

Wayland 和 X11 最关键的几点不同

没有服务器端绘图

协议里没有"画线、画字"这类请求，应用必须自己渲染整张窗口。这把 X11 里早已没人用的大量历史包袱一并扔掉了。

换窗口管理器 = 换合成器

窗口策略在合成器内部，不再有独立的窗口管理器进程。想要平铺就用 Sway、Hyprland、niri，想要传统桌面就用 GNOME 的 Mutter 或 KDE 的 KWin。很多合成器基于 wlroots、Smithay 等库构建，参考实现是 Weston。

应用之间互相隔离

X11 里任何程序都能读取整个屏幕、监听全局按键、向别的窗口注入输入，等于没有隔离。Wayland 客户端只能看到自己的窗口。截图、录屏、远程控制要通过 xdg-desktop-portal + PipeWire 申请，并由用户授权。

XWayland 保兼容

XWayland 是跑在 Wayland 合成器里的一个 X Server。老的 X11 程序连上它照常工作，它再把这些窗口当作普通 Wayland 窗口交给合成器。用 xlsclients 列出的就是走 XWayland 的程序。

协议本身不管网络

没有 ssh -X 那样的网络透明。远程运行单个程序用 waypipe，远程桌面用 RDP 或 VNC（gnome-remote-desktop、KDE 的 KRdp、wlroots 系的 wayvnc）。

现代显示特性更顺

多块屏用不同缩放比例（混合 DPI）、不同刷新率、分数缩放、可变刷新率、HDR，在 Wayland 上实现得更自然；X11 只有一个全局坐标系和一套全局设置。

老程序原生支持通过 XWayland

现状（截至 2026 年）：Fedora、Ubuntu 等主流发行版的 GNOME 和 KDE 桌面默认早已是 Wayland 会话。GNOME 从 49 版开始默认不再提供 X11 会话，KDE 也宣布 Plasma 6.8 起只支持 Wayland。NVIDIA 专有驱动在 555 版加入显式同步之后，Wayland 体验大幅改善。Xorg 本身基本只剩维护性更新，但 Xvfb、Xvnc 和 XWayland 仍会长期存在，所以 X11 的概念还值得懂。

动手查看

在自己的机器上验证这些概念

# 我现在是 X11 还是 Wayland？
echo $XDG_SESSION_TYPE                 # x11 / wayland / tty
echo "$DISPLAY | $WAYLAND_DISPLAY"     # 例如 ":0 | wayland-0"

# 显卡和驱动
lspci -k | grep -EA3 'VGA|3D|Display'  # 显卡型号 + 正在用的内核驱动
ls -l /dev/dri/                        # card0 = 显示控制，renderD128 = 渲染
glxinfo -B                             # OpenGL 渲染器和 Mesa 版本（mesa-utils 包）
vulkaninfo --summary

# 显示器
xrandr                                 # X11 下列出输出口、分辨率、刷新率
for f in /sys/class/drm/card*-*/status; do echo "$f: $(cat $f)"; done

# 窗口管理器 / 桌面环境
wmctrl -m
echo $XDG_CURRENT_DESKTOP

# 哪些程序走 XWayland（Wayland 会话里）
xlsclients

# 虚拟显示：在内存里开一块 1280x720 的屏，跑一个时钟
Xvfb :99 -screen 0 1280x720x24 &
DISPLAY=:99 xclock &
DISPLAY=:99 import -window root shot.png   # 截下虚拟屏（ImageMagick）
xvfb-run -a python run_selenium_tests.py   # 一条命令包装

# VNC
vncserver :1 -geometry 1920x1080       # TigerVNC：新建独立虚拟桌面，端口 5901
x11vnc -display :0 -localhost          # 共享当前真实桌面，只监听本机
ssh -L 5901:localhost:5901 user@server # 在自己电脑上开隧道，然后连 localhost:5901
常见误区

容易搞混的五件事

X Server 跑在远程服务器上
X Server 跑在有屏幕和键盘的那台机器上。远程跑的程序是 X 客户端，它连回你本地的 X Server。
显卡驱动就是一个内核模块
完整的驱动分三块：内核里的 DRM/KMS 驱动，用户态的 Mesa（或 NVIDIA 专有库），再加 Xorg 的 DDX 模块（通常是通用的 modesetting）。
服务器没有显示器就跑不了图形程序
用 Xvfb、Xvnc 或合成器的 headless 后端开一块虚拟屏即可，CI 里的浏览器测试天天这么跑。
VNC 和 ssh -X 是一回事
VNC 传整屏像素，与应用无关；ssh -X 传的是 X 协议命令，只转发单个程序的窗口，而且在 Wayland 下需要 XWayland 或改用 waypipe。
Wayland 是 Xorg 的新版本
它是一套全新的协议，和 X11 不兼容。接替 Xorg 位置的，是 Mutter、KWin、Sway 这些各家自己实现的合成器；老程序靠 XWayland 兼容。
